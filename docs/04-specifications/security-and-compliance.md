# الأمان والامتثال والتحكم في الوصول (Security & Compliance)
## منصة «أثر» — بلدية المنصورة (العقدة التشغيلية الأولى)

---

## 1. نموذج نمذجة التهديدات (STRIDE Threat Model)

تم تحليل المنظومة الأمنية لنظام «أثر» لتحديد المخاطر المحتملة الخاصة بمنصات التحفيز البيئي وإدارة النفايات:

| التهديد (Threat) | الخطر في سياق مشروع «أثر» | إجراءات الحماية والمعالجة التقنية |
| :--- | :--- | :--- |
| **Spoofing (انتحال الهوية)** | انتحال صفة مواطن لصرف نقاطه، أو انتحال صفة عامل ميداني لتسجيل أوزان وهمية. | • مصادقة بالهاتف عبر رموز SMS OTP لمرة واحدة مع تشفير الجلسات.<br/>• دعم التحقق بخطوتين (2FA) كخيار أمان إضافي لحسابات الإدارة، مع فرض صلاحيات الأدوار الصارمة (RBAC).<br/>• تسجيل المعرّف المرجعي للميزان الميداني (`scale_reference`) وربطه بعهدة العامل. |
| **Tampering (التلاعب بالبيانات)** | التلاعب بقراءات الميزان أو تعديل قيود الأستاذ العام لإضافة نقاط من العدم. | • تطبيق خوارزمية رصد الشذوذ الوزني، وتدقيق المشرفين الإداريين للأوزان المشتبهة خلال 24 ساعة، مع إرفاق صورة الإثبات التوثيقية.<br/>• قيود الأستاذ العام (Green Points Ledger) غير قابلة للتعديل أو الحذف (Append-Only).<br/>• تشفير المعاملات الحساسة بتوقيع رقمي ومفاتيح منع التكرار (Idempotency). |
| **Repudiation (التنكر والإنكار)** | إنكار المواطن استلام السلعة أو إنكار التحويل البنكي أو النقاط. | • سجل تدقيق صارم غير قابل للتعديل (`audit_logs`) يسجل عنوان الـ IP وبصمة المتصفح والطابع الزمني الصارم.<br/>• توثيق التوقيع الإلكتروني وتأكيد سند التحويل للطلبات وسجلات الوزن. |
| **Information Disclosure (تسريب البيانات)** | تسريب أرقام هواتف المواطنين أو إحداثيات منازلهم في المنصورة. | • تشفير البيانات التعريفية (PII) في قاعدة البيانات بخوارزمية `AES-256-GCM`.<br/>• استخدام الفهرسة العمياء `HMAC-SHA256 Blind Indexing` للبحث دون كشف النص الصريح.<br/>• تطبيق TLS 1.3 لجميع الاتصالات الشبكية. |
| **Denial of Service (حجب الخدمة)** | إغراق بوابات الـ API بطلبات وهمية لتعطيل تطبيق عمال النظافة. | • محدد معدل الطلبات الموزع (Redis Rate Limiting) بمعدل 100 طلب/دقيقة للـ IP.<br/>• عزل طوابير المهام الخلفية (BullMQ) عن خادم الـ API ومعالجة الإشعارات والعمليات الثقيلة بشكل غير متزامن. |
| **Elevation of Privilege (تصعيد الصلاحيات)** | محاولة مستخدم عادي أو عامل الوصول إلى لوحات تحكم المشرفين أو المالية. | • تطبيق صارم للتحكم في الوصول القائم على الأدوار (RBAC) مع التحقق في طبقة التوجيه (Fastify Pre-Handler Hooks). |

## 3. معايير التشفير وحماية البيانات الحساسة (Cryptography & PII Protection)

### 3.1 تشفير البيانات أثناء السكون (Encryption at Rest):
* يتم تشفير الأعمدة الحساسة (`phone_number`, `two_factor_secret`, `coordinates_raw`) في قاعدة بيانات PostgreSQL باستخدام خوارزمية **AES-256-GCM** مع مفتاح تشفير عالي الأمان يُدار عبر متغيرات البيئة (`DATA_ENCRYPTION_KEY`).
* يُحفظ متجه التهيئة الفريد (Initialization Vector - IV) ورمز التحقق (Auth Tag) بجانب كل قيمة مشفرة لمنع التلاعب بالنصوص المشفرة.

### 3.2 تقنية الفهرسة العمياء للبحث المشفر (Blind Indexing):
للتمكن من البحث عن رقم الهاتف بسرعة فائقة في قاعدة البيانات عبر استعلام `SELECT * FROM users WHERE phone_bindex = ?` دون فك تشفير كافة السجلات ودون تخزين الرقم بصيغته المكشوفة:
$$\text{phone\_bindex} = \text{HMAC-SHA256}(\text{E.164 Phone Number}, \text{BLIND\_INDEX\_PEPPER})$$

### 3.3 حماية كلمات المرور والرموز السرية (Secret Hashing):
* تُجزأ الرموز الدائمة وكلمات مرور المشرفين باستخدام خوارزمية **Argon2id** (بمعاملات: Memory=64MB, Iterations=3, Parallelism=2).
* تُجزأ رموز التحديث (Refresh Tokens) ورموز التحقق المؤقتة في الذاكرة باستخدام **SHA-256**.

## 4. سياسة المصادقة وتفويض الصلاحيات وضوابط التحقق الثنائي (Authentication & 2FA Policy)

* **المصادقة الأساسية الموحدة (Primary Factor):** تعتمد المنظومة على التحقق المباشر برمز لمرة واحدة عبر الرسائل القصيرة (**SMS OTP**) لكافة مستخدمي المنظومة (المواطنين والعمال الميدانيين وموظفي الإدارة)، مع ضبط معدل الطلبات وحماية الجلسات وتطبيق التحكم الصارم في الوصول القائم على الأدوار (**RBAC**).
* **التحقق الثنائي كإجراء إضافي اختياري (Optional Administrative 2FA):** يُتاح تفعيل المصادقة الثنائية المستندة إلى الوقت (Time-Based One-Time Password - TOTP عبر RFC 6238) كخيار أمان إضافي اختياري لحسابات الإدارة الحساسة (مثل مدير النظام العام والمراقب المالي) لتعزيز الأمان عند الحاجة، دون أن يكون قيداً إلزامياً يعطل التشغيل الميداني أو العمليات الأساسية.
* في حال تفعيل الـ 2FA لحساب إداري، يتم التحقق من الرمز الإضافي عبر تطبيقات المصادقة القياسية (مثل Google Authenticator) مع نافذة تسامح زمنية (Time Drift Window) مقدارها $\pm 1$ خطوة زمنية (30 ثانية).

## 5. نزاهة سجلات التدقيق الرقابي (Immutable Audit Trails)

* جدول `audit_logs` محمي على مستوى قاعدة البيانات بمنع أوامر `UPDATE` و `DELETE` نهائياً عبر Triggers صارمة:
```sql
CREATE OR REPLACE FUNCTION prevent_audit_log_modification()
RETURNS TRIGGER AS $$
BEGIN
    RAISE EXCEPTION 'Audit logs are strictly immutable and cannot be updated or deleted!';
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_protect_audit_logs
BEFORE UPDATE OR DELETE ON audit_logs
FOR EACH ROW EXECUTE FUNCTION prevent_audit_log_modification();
```
* يتم تسجيل كل عملية حساسة متضمنةً: `actor_id`, `action`, `before_state`, `after_state`, `ip_address`, و `created_at`.
